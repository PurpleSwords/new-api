# Responses WebSocket 单实例容量规划

本文记录当前 fork 在单实例服务器上部署 Responses WebSocket 中继时的容量评估与首发限制建议。评估日期为 2026-08-08，结论基于服务器实测和代码检查，尚未经过专门压测，不代表上游项目默认配置或性能承诺。

## 结论

当前应用和 Caddy 都没有设置 WebSocket 连接数量上限。连接会被持续接受，直到内存、CPU、数据库、Redis 或上游服务先成为瓶颈。操作系统能够接受的 socket 数量远高于这台服务器能够稳定处理的活跃请求数，因此不能将文件描述符上限直接视为业务容量。

建议首发使用以下限制：

| 限制维度 | 建议值 | 说明 |
| --- | ---: | --- |
| 单令牌已建立连接 | 16 | 支持约两组“主线程 + 6 个子代理”的 Codex 会话，并保留重连余量 |
| 单用户已建立连接 | 32 | 防止用户通过多个令牌绕过单令牌限制 |
| 全局已建立连接 | 128 | 控制空闲连接、socket 和 goroutine 的总占用 |
| 全局活跃请求 | 40 | 控制正在执行 `response.create` 的请求，保护 CPU、Redis、数据库和上游通道 |
| 业务空闲超时 | 30 分钟 | 回收长时间没有业务消息的连接；正常客户端可以自动重连 |

“已建立连接”指已经完成 WebSocket Upgrade、仍保持打开的连接；“活跃请求”指正在处理一次 `response.create`、尚未收到成功或失败终态的连接。二者需要分别计数，因为大量空闲连接主要消耗内存和文件描述符，而大量活跃请求还会同时消耗 CPU、数据库连接和上游额度。

这些值是保护性首发阈值，不是压测得到的最大吞吐量。实现前不会自动生效。

## 多用户容量换算

Codex 一个主线程加最多 6 个子代理，按最坏情况约占用 7 条 WebSocket 连接。基于上述阈值：

- 全局 128 条已建立连接可容纳约 18 组完整会话保持在线。
- 全局 40 个活跃请求可容纳约 5 组完整会话同时满负荷生成。
- 实际连接通常不会全部同时生成，当前服务器预计适合约 10 至 20 名间歇使用的用户。
- 如果多人长期同时运行大量子代理，2 核 CPU 会先于文件描述符成为瓶颈。

这里的“用户数”只用于容量换算。实际可用人数还取决于模型响应速度、上下文大小、消息频率、数据库延迟和上游并发限制。

## 服务器实测

当前单实例服务器的关键资源如下：

| 项目 | 实测值 |
| --- | --- |
| CPU | 2 vCPU |
| 内存 | 1.9 GiB，总可用约 1.2 GiB |
| Swap | 2.0 GiB，已使用约 70 MiB |
| Docker 资源限制 | 未设置 CPU、内存或 PID 配额 |
| 应用进程文件描述符 | soft 524287，hard 524288 |
| Caddy 文件描述符 | 1048576 |
| `somaxconn` | 8192 |
| `nf_conntrack_max` | 1000000 |
| 当前 TCP 状态 | 数量很少，不构成现时压力 |

文件描述符和内核连接跟踪上限都不是当前首要约束。对于 2 vCPU、1.9 GiB 内存的机器，实际约束更可能依次来自活跃流的 CPU 消耗、Redis/数据库结算路径、上游限制和连接内存。

## 单连接成本

一条已经开始工作的 Responses WebSocket 会话在 new-api 进程内具有以下确定成本：

- 一条客户端到 new-api 的 WebSocket socket。
- 一条 new-api 到上游服务的 WebSocket socket，不与其他会话复用。
- 两个长期 goroutine：客户端读取循环和上游读取循环。
- 一个会话状态对象和一个 WebSocket 管理器注册项。
- 每次 `response.create` 的请求、用量、计费和输出文本临时对象。
- 同一连接同一时刻最多处理一个 `response.create`；更多并发需要建立更多连接。

Caddy 位于客户端和 new-api 之间，因此端到端还会在 Caddy 进程中占用客户端侧和上游侧连接。粗略估算每条空闲端到端连接约占 300 至 700 KiB，但该数值受内核缓冲、TLS、消息大小和 Go 堆状态影响，必须通过实际监控或 pprof 校准。

## 当前配置与风险

Caddy 当前仅对 new-api 反向代理设置了 `flush_interval -1`，用于低延迟流式转发。没有配置 `max_conns_per_host`、`stream_timeout` 或 WebSocket 并发上限，因此 Caddy 不会代替应用执行上述保护。

Responses WebSocket 会默认每 30 秒向客户端发送一次标准 WebSocket Ping 控制帧，客户端需要回复 Pong；空闲等待期间连续三倍间隔未收到 Pong 时关闭连接。可以通过 `RESPONSES_WS_PING_INTERVAL_SECONDS` 调整间隔，最大值为 `3600`，设置为 `0` 或负数可以关闭。该机制只保护客户端到 new-api 的连接，不改变 new-api 到上游的连接行为。配置在进程启动时读取，修改后需要重启。

代码侧当前还存在以下容量风险：

- 握手路径没有连接并发限制。
- 上游读取仍没有业务空闲超时、读写 deadline 或主动 ping/pong 存活检测。
- WebSocket 消息没有读取大小上限，异常大消息可能造成单连接内存突增。
- 输出文本会在一次调用期间持续累积，长输出会增加堆内存占用。
- 客户端写入没有 deadline，慢客户端可能阻塞上游读取 goroutine。
- Caddy reload 默认会关闭活动 WebSocket；客户端应能够自动重连。

这些风险意味着即使平均每条空闲连接占用不高，也不能在缺少应用层保护时直接开放上千条连接。

## 实现边界

连接保护应至少分为以下两层：

1. 在 WebSocket Upgrade 之前执行单令牌、单用户和全局已建立连接限制。超过限制时返回 HTTP 429，并确保所有退出路径都释放计数。
2. 在接受 `response.create` 时执行全局活跃请求限制，在成功、失败、客户端断开和上游异常的所有终态释放计数。

客户端连接已经通过标准 Ping/Pong 控制帧检测静默断线。后续仍需增加业务空闲超时、上游连接存活检测、合理的写 deadline 和消息读取上限。读取上限需要结合允许的最大上下文载荷确定，不能直接使用未经验证的固定值。

单用户限制不能由单令牌限制替代，因为同一用户可以创建多个令牌。IP 限制也不适合作为主要维度，多名用户可能位于同一 NAT 或公司网络之后。

## 监控与调整

首发后至少监控以下指标：

| 指标 | 告警参考值 |
| --- | --- |
| CPU | 持续 5 分钟超过 70% 告警，超过 85% 视为扩容信号 |
| 可用内存 | 低于 500 MiB 告警，低于 300 MiB 视为高风险 |
| 活跃请求 | 达到 32 个，即首发全局上限的 80% |
| 已建立连接 | 达到 102 条，即首发全局上限的约 80% |
| 限流拒绝 | 5 分钟内出现持续拒绝时检查是否为单用户异常或整体容量不足 |
| Redis/数据库延迟 | 关注请求结束时的计费和结算延迟，以及连接池等待 |

在 CPU、内存、Redis、数据库和上游错误率均稳定的前提下，可以逐步将全局已建立连接提高到 256、全局活跃请求提高到 60。每次只调整一个层级并观察至少一个业务高峰；如果活跃请求达到 40 时 CPU 已经持续接近 85%，应优先升级服务器或拆分实例，而不是继续提高限制。
